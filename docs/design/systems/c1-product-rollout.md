# C1 제품 전환·의뢰 보상 배치 통합안

- 2026-09-27 / Codex 구현·통합. **디렉터가 권고안대로 구현 승인: C1 곡선·공급 정책 채택, 기본 V3 저장 전환, 보스 기준 우선 Lv95 유지.** A~C와 전환 설계 독립 검토 통과 후 D 구현. [D 통합 보고서·검토 요청](../../qa/c1-product-implementation-review-request.md).
- 의존: [저장 계약](c1-save-migration.md) · [EXP 공급 목표](../100-hour-exp-margin.md) · [장별 예산](../100-hour-progression-budget.md) · [의뢰 구조](../quests/quest-structure.md).
- 변경 이력: 저장 후보 검증 A~C 통과 이후 남은 실제 전환·보상 배치·저장 상태 정책을 하나로 묶었다. 현행01~03·곱셈 곡선·기본 V2 파일은 바꾸지 않았다.

## 1. 무엇을 결정하는가

C1은 Lv1~10의 기존 EXP와 만렙100·전직10/40/80을 보존한다. 디렉터의 “그럼 그대로 구현해라”에 따라 **C1과 아래 공급 정책을 함께 채택**했다. 저장 후보 검토를 채택 승인으로 간주한 것이 아니라 별도 디렉터 결정으로 적용한다.

이 문서는 채택안의 구현 계약이다.100h 완주·약22h의3차 사용 구간을 실측했다고 주장하지 않는다. 최종전 기준95를 우선 유지하고 기준 경로98/A96/B95의 체감 난도는 실제 콘텐츠에서 후속 검증한다.

## 2. 설계 슬롯을 의뢰 ID에 배정하는 안

아래 ID는 **신규 설계 예약안**이다. 현재 카탈로그에 등록됐거나 실행 가능한 의뢰가 아니다. 기존61건 목표 안의 자리이며 의뢰 수를 추가하지 않는다.7장6건/11장5건/12장5건이라는 기존 예산 범위 안에서 번호를 골랐다. 제목·스토리 세부·NPC/목표 target ID는 이번에 만들지 않는다.

| 슬롯 | 예약 의뢰 ID | 의뢰 선행 예약 | 기존 메인 보고 EXP | 신규 추가 EXP | 해당 보고 총 EXP | 추가 조건 |
| --- | --- | --- | ---: | ---: | ---: | --- |
| S7 | MQ-07-01 | MQ-06-05 | 500000 | 500000 | 1000000 | 해당 전직 없이 조사·보고 가능 |
| S11 | MQ-11-01 | MQ-10-05 | 1000000 | 2060000 | 3060000 | 해당 전직 없이 조사·보고 가능 |
| S12 | MQ-12-04 | MQ-12-03 | 0 | 2799780 | 2799780 | 최종전 진입 전에 보고 완료 가능 |
| 승리 보고 | MQ-12-05 | MQ-12-04 | 250000 | 0 | 250000 | 최종 보스 처치도 완료 조건으로 요구 |

선행 ID도 설계 예약이다. 현행 `QuestData.prerequisite`는 단일 문자열이므로 표의 의뢰 간 선행은 그 구조에 맞춘다. 승리 보고의 보스 처치는 선행 문자열에 복합식을 넣지 않고 별도 KILL 목표로 설계한다. 실제 boss target/source·NPC가 없는 지금 `.tres`를 만들어 로드하거나 자동 완료시키지 않는다.

S7/S11은 REACH/TALK 등 현재 지원 목표로 먼저 접근 가능한 조사 보고를 설계한다. 서브·종족 선택·특정 직업·Lv40/80 전직·최종 보스 완료를 조건으로 넣지 않는다. 미전직 모험가도 보고할 수 있어야 한다. 장 진입과 첫 보고 사이 전투가 요구 레벨을 선행하는 순환도 실제 맵에서 검사한다.

### 중복 배분 방지

| 장 | 기초 메인 보고 풀 | 예약 보고에 쓰는 기초분 | 남은 기초 보고 풀 | 추가 EXP |
| --- | ---: | ---: | ---: | ---: |
| 7 | 1317896 | 500000 | 817896 | 500000 |
| 11 | 4716185 | 1000000 | 3716185 | 2060000 |
| 12 | 5926865 | 250000 | 5676865 | 2799780 |

7·11장 잔여는 나머지 메인 의뢰 제작 예산이지 같은 양을 또 지급하는 보상이 아니다.12장 잔여5,676,865는 MQ-12-01~03 보고에 배정하고 S12 전까지 수령 가능한 동선을 설계한다. 구체 건별 분배는 목표/NPC/소요시간 정의와 함께 확정한다. 표의 남은 풀을 개별 의뢰 전부에 그대로 복사하지 않는다.

최종 보스 처치250,000은 **보고 풀이 아닌 처치 풀**에서 별도로 남긴다. 승리 보고250,000과 합한500,000을 G95 진입 공급에서 제외한다.12장 서브 보고3,951,243 및 처치3,983,475(전체4,233,475−최종 처치250,000)의 기준 경로 공급 역시 S12 전에 얻을 수 있어야 기존 모델이 성립한다. 서브 생략 A/B 손실은 그대로 적용한다. 이 큰 사전 공급 요구가 실제 동선에 수용되지 않으면 모델/배치를 다시 검토하며, 보스 후 보상을 미리 지급해 숫자만 맞추지 않는다.

앞 절의 12장 최종전 전 기준 공급은 **16,411,363 EXP**(5,676,865 + 2,799,780 + 3,951,243 + 3,983,475)다. 11장 기초 풀11,229,013 대비1.461배이나, 증액 후 11장13,289,013(기초 + S11 2,060,000)과 동일 기준으로 비교하면 **1.235배**다. 두 장 모두 시간 예산11h이며, 12장 전체16,911,363 중 **97.04%**를 최종전 전에 확보해야 한다. 이는 공급 배치 압력이지 실제 시간당 획득량 실측이 아니다. 보스전 시간을 제외한 실제 사전 동선의 소요시간과 A/B 공급을 따로 측정한다.

## 3. 보상 버전과 기존 저장 상태

**현재 출시된 MQ-01-01~03의 ID·목표·보상은 전부 유지**한다. V1/V2→V3는 곡선 변환이며 보상 지급 이벤트가 아니다. S7/S11/S12를 업그레이드 보상으로 주지 않는다.

| 저장 상태 | 적용 정책 |
| --- | --- |
| V1 의뢰 예약 `{}` | 기존 정책 유지. 신규 예약 의뢰 수락/완료 상태를 만들지 않음 |
| V2/V3의 기존01~03 active/ready | 목표·counts·기존 보상 그대로, 정상 보고 시 기존 금액 지급 |
| 기존01~03 completed | 완료 유지. 재지급·보상 차액 지급 없음 |
| 신규 예약 ID 미수락 | 콘텐츠 정식 등록 후 정상 선행/명시 수락 경로에서만 시작 |
| 현재 카탈로그에 없는 예약 ID가 파일에 존재 | 현재의 미등록 의뢰 거부/파일 보호 유지. ID를 삭제하거나 완료로 추정하지 않음 |

새 예약 ID는 현행 정상 저장에 존재할 수 없으므로 이번에 모든 의뢰 상태에 reward_version 필드를 추가할 필요는 없다. **최초 등록 보상 계약은 ID에 고정**하고 출시 후 바꾸려면 별도 콘텐츠 버전·active/ready/completed 변환 정책을 먼저 설계한다. V3 숫자만 보고 특정 보상을 받은 것으로 추정하지 않는다. 이미 배포된 보상을 몰래 교체하는 근거로 이 방침을 사용하지 않는다.

현재 보고는 NPC 일치·ready·보상 유효성·가방 여유를 검사하고, 보상 지급 중 저장을 막고, 완료로 바꾼다. completed 재보고는 거부한다. 메모리 동기 지급과 캐릭터 스냅샷 복원을 보존한다. **파일 저장 전 프로세스 종료는 마지막 저장으로 되돌아가는 정책**이며 보고 즉시 디스크 트랜잭션을 추가한 것으로 주장하지 않는다. 지급 중 예외·실패 후 부분 지급 방지 검증은 새 보상/목표 등록의 회귀 항목이다.

## 4. 제품 전환은 함께 바꿔야 한다

C 리뷰 당시 “상수 두 개와 character_version만 바꾸면 끝”은 실제 변경 목록으로 부족했다. 아래 전체 묶음을 D에서 적용했다. 현재 기본 schema·prepare_loaded·LevelCurveData는 모두 C1/V3 제품 경로에 연결돼 있다.

| 변경 묶음 | 전환 시 필요한 작업 |
| --- | --- |
| 런타임 | LevelCurveData에 구/C1 프로필을 명시적으로 구분하고 배포 `.tres`만 C1 선택. 기본 프로필은 구 규칙으로 유지해 역사 fixture를 재현. 저장 스냅샷에 런타임이 의존하게 만들지 않음 |
| schema/codec/migration | 기본 character_error 지원3, 기본 prepare_loaded의 원본 검증→C1 변환→V3 재검증, capture3, restore_into의 V3 검사. 후보 API와 기준이 갈리지 않게 정리 |
| store/session | 출력3/지원1·2·3/character_version3을 같은 커밋에서 전환. 현재 일반화된 보류 판정·원본 버전 보관은 재사용 |
| 현재 출력 테스트 | V2 쓰기38곳·store probe2곳·현재 capture 함수명·마이그레이션 probe 라벨을 **현재 출력 검사만** V3로 변경 |
| 역사 fixture | V1/V2 원본 봉투·구REQ154,381,573 단언·초반18,612 유지. 현행 배포 `.tres`와 구 규칙 fixture를 구분해 검사 |
| QA 계산기·테스트 | `m3_phase_d_balance_calc.py`·`m3_respawn_pace_calc.py`의 `req()`에 구/C1 프로필 분기를 구현. C1의 L11~19 배율 `0.4^((L-10)/10)`은 현행 단일 수식에 없으므로 `.tres` 필드 선택만으로 전환되지 않음. `test_m3_exp_calculators.py`도 배포 C1 검증과 명시적 Legacy fixture 검증으로 분리하고 구99값 단언은 보존. 현행 초반 배율·반올림 수정은 `4409236` 완료. D에서 각 프로필99값·경계9/10/11/19/20를 실제 엔진 출력과 대조 |
| 회귀 | 기본 제품 경로 자체로 구 저장 로드/수동 저장/재실행/혼합 세대 복구를 재실행. 후보 통과를 그대로 제품 통과로 인용하지 않음 |

저장 전환 패치와 C1 런타임은 같은 구현 묶음으로 적용한다. 미래 장 공급 정책은 채택했으나 예약 의뢰를 임시로 등록하거나 소급 지급하지 않는다. 전환 후 V3 저장을 만든 사용자가 구 빌드를 실행하면 구 빌드는 거부한다. 자동 다운그레이드는 제공하지 않는다. QA는 계속 격리 저장 폴더를 사용하며 실제 사용자 저장은 테스트하지 않는다.

## 5. 승인/검증 체크리스트

- 설계 검토: 예약 ID·단일 선행 구조·장별 잔여 풀·기존 저장 무소급 정책·전환 목록을 함께 검토한다.
- 콘텐츠 제작: 각 예약 의뢰의 실제 NPC/target/source/접근 맵을 정하고 모든 지원 직업의 선행 그래프를 검사한다. 등록 전에는 콘텐츠 검증을 통과했다고 하지 않는다.
- 페이스:7/11장 첫 보고의 실제 소요시간, 보고 직후 전직 메뉴 접근,12장 사전 보고/처치 공급과 생략 경로를 측정한다. 모델≥1%가 실제 페이스 보장은 아니다.
- 디렉터 결정 완료: C1/공급 정책 채택과 기본 V3 전환, 보스 기준 우선95 유지. 실제 후반 난도와 콘텐츠 접근성 검증은 남는다.
- D 검증: 기본 제품 전환 원자성(빌드 단위), 전 버전/전 레벨·직업/의뢰 상태, 수동 실패 원본 보존, 실제 실행·종료. G4/G5 이월 항목은 별도로 남긴다.
