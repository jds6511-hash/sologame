# M4 저장·불러오기 계약과 G4 기준

- **최종 수정일**: 2026-09-21
- **담당**: Codex 구현·통합 / Claude 독립 검토
- **의존 문서**: [로드맵](../DEVELOPMENT_ROADMAP.md), [개척자의 유산](pioneer-legacy.md), [실행 계획](../../superpowers/plans/2026-09-21-m4-save-load.md)
- **변경 이력**: 2026-09-21 최초 작성. Claude H1~H4·M1~M5와 검증 누락을 기존 코드에 대조해 반영.

## 1. G4 단일 완료 기준

1. 모험가·전사·궁수·검투사의 새 게임→진행→저장→프로세스 종료→재실행→불러오기에서 레벨·EXP·직업·강화·실제 스킬 지출·가방·8장비 슬롯·골드·HP/MP·맵·위치·날짜/시각이 복원된다. 반복 저장에도 값이 흐트러지지 않는다.
2. 계정 파일과 10개 캐릭터 파일을 분리한다. A 저장이 B를 바꾸지 않고, 새 캐릭터는 초기 진행과 새 ID를 가진다. 계정의 실제 연결은 튜토리얼 완료 기록이며 아직 업적·도감 게임플레이는 구현하지 않는다.
3. 파싱·체크섬·필수 필드·자료형·범위·ID·장비 슬롯·스킬 지출 검증을 통과한 상태만 적용한다. 실패하면 현재 게임과 원본 저장을 바꾸지 않는다.
4. 정상 이전본 백업, 임시 파일 중단, 파일 교체 실패, 쓰기 실패를 검사한다. 각 파일은 독립적으로 복구되며 계정 손상을 캐릭터 초기화로 숨기지 않는다.
5. 미지원 하위/상위 버전을 명시적으로 거부하며 원본을 보존한다. 저장/로드 결과를 UI에서 알리고 사망·전직·전투 동작 중 저장은 금지한다.
6. GUT·린트·월드 입력 회귀와 별도 프로세스 복원을 통과하고 디렉터의 플레이 판정을 별도로 기록한다.

기존 PROJECT_STATUS 11-2와 로드맵의 간략 완료 문구는 이 기준을 참조한다. 유산 11장의 도감·칭호·창고·보너스 콘텐츠 검증은 M11/M14/M15 대상이며 M4 완료로 주장하지 않는다.

## 2. 파일과 식별자

- `user://saves/account.json`, `character_01.json`~`character_10.json`. 계정 1개만 지원한다.
- 계정 ID와 캐릭터 ID는 OS 암호학적 난수 16바이트의 hex 문자열로 발급한다. 슬롯 번호는 저장 위치이며 캐릭터 정체성이 아니다.
- 슬롯 11은 거부한다. 찬 슬롯에 새 캐릭터를 저장하려면 덮어쓰기 확인이 필요하며 새 캐릭터 ID를 발급한다. 독립 삭제 UI는 M4 필수가 아니며 계정 삭제 UI도 제공하지 않는다.
- 저장 봉투는 `kind`, `version`, UTF-8 JSON `payload`, SHA-256 `checksum`이다. 체크섬은 우발적 손상 탐지이며 위변조 방지 보안 장치가 아니다.
- 각 종류의 현재 버전은 1. 출시된 이전 저장 형식이 없으므로 버전 0도 거부한다. 이후 버전 추가 시 명시적 순차 마이그레이션과 원본 보존 테스트를 함께 추가한다.
- 계정/캐릭터 버전은 종류별로 검사하며 양쪽이 지원될 때만 함께 연다. 버전 숫자가 서로 같아야 한다는 규칙은 두지 않는다. 캐릭터의 `account_id`가 계정과 다르면 거부한다.

## 3. 저장 본문

| 소유자 | 필드 |
|---|---|
| 계정 | account_id, account_save_version, clear_count, discoveries, achievements, cosmetics, seen_content, tutorial_completed, legacy, storage, pending_transfer, applied_transfer_ids |
| 캐릭터 | character_id, character_save_version, account_id, name, play_seconds, player, inventory, world, progress, tutorial, pending_transfer, applied_transfer_ids |
| player | level, exp, job_id, hp, mp, skill_points, spent_points, skill_levels, skill_costs |
| inventory | gold, bag(item_id/quantity), equipment(문자열 슬롯 ID→item_id) |
| world | map_id, position[x,y], day_number, elapsed_real_sec_in_day, flags, discovered_regions |
| progress | quests, reputation, territory, story_flags, first_death_waiver_used |
| tutorial | tutorial_done, hint_heal_done — 캐릭터별 실제 이행 여부 |

- 계정의 tutorial_completed는 누적 기록이다. 새 캐릭터 자동 스킵 권한은 첫 엔딩 해금 때 구현한다. M4에서는 새 캐릭터가 튜토리얼을 다시 수행한다.
- 레벨 1~100, EXP는 해당 레벨 필요량 미만(만렙은 0), 골드·수량·포인트는 유한한 0 이상 정수, 상한은 2^31−1. 날짜는 1 이상, 하루 내 경과는 0 이상 하루 길이 미만. 위치·HP/MP·플레이 시간은 유한수로 제한한다.
- 등록된 직업의 전직 레벨을 충족해야 하며 미등록 스킬·아이템·맵은 거부한다. 스킬별 지출 합과 spent_points, 성장/전직으로 얻는 총 포인트도 대조한다.
- 장비 키는 weapon/body/legs/head/feet/ring_1/ring_2/necklace로 고정한다. enum 순번을 파일에 쓰지 않는다. 아이템·스킬 레지스트리가 stable ID를 실행 리소스로 변환한다.

## 4. 실패와 복구

1. 동일 디렉터리의 `.tmp`에 기록하고 flush/close 후 다시 검증한다.
2. 기존 주 파일이 정상일 때만 `.bak.tmp`에 복사·검증하고 `.bak`으로 교체한다.
3. `.tmp`를 주 파일로 rename한다. 교체의 OS별 원자성을 보장하지 않으며, 주 파일이 사라진 경우 정상 `.bak`이 복구 안전망이다. 실패를 성공으로 표시하지 않는다. OS 전체 전원 손실의 저장 장치 내구성까지 보장한다고 주장하지 않는다.
4. 로드 시 주 파일의 파싱·체크섬 또는 스키마가 잘못됐으면 정상 백업을 검사한다. 복구본 사용 여부를 명시한다. 미지원 버전은 백업으로 몰래 되돌리지 않는다.
5. 백업도 실패하면 로드를 거부한다. 손상 계정을 빈 계정으로 자동 대체하지 않는다. `.tmp`만 존재하는 첫 저장 중단은 미완 저장으로 취급하며 자동 채택하지 않는다.
6. 미지원 주 파일은 덮어쓰기를 거부한다. 미지원 백업만 남았다면 해당 원문을 `.bak.preserved.<SHA-256>`으로 보존·재검증한 뒤 새 저장을 허용한다. 이후 백업 회전에도 보존본은 삭제하지 않는다. 자동 저장의 손상/미지원 슬롯 차단은 유지하며, 슬롯 재사용은 향후 UI의 명시적 수동 저장 확인 경로에만 연결한다.
7. 현재 검증기에서 `invalid_data`가 된 주 파일/백업은 각각 `.preserved.<SHA-256>`으로 보존한 뒤 교체한다. 보존 실패 시 저장을 중단한다. `.bak`에는 현재 검증을 통과한 정상 주 파일만 넣는다. 보존본은 자동 로드하지 않으며 원인 조사·후속 마이그레이션용이다. 기존 정상 데이터를 거부하는 규칙 변경은 원칙적으로 버전 상승과 마이그레이션으로 처리하고, 보존본은 그 대체가 아닌 추가 안전망이다.
8. payload 4 MiB와 직렬화한 전체 봉투 8 MiB를 각각 쓰기 전에 검사하며 초과는 `too_large`로 반환한다. 검증기는 `Callable(Dictionary) -> String`이며 빈 문자열만 성공이다. 호출 불가/잘못된 반환형은 `invalid_validator`로 거부한다.
9. 실패/강제 종료 시 `.tmp`·`.bak.tmp`와 보존본 `.tmp`가 남을 수 있다. 이를 슬롯으로 표시하거나 자동 복구본으로 채택하지 않는다. 같은 대상 재시도 때 갱신하며, 완성된 보존본은 내용 해시별로 중복 생성하지 않는다. 읽기의 슬롯 기본값 0은 계정용 편의이고, 쓰기는 대상을 명시하도록 슬롯 인자를 필수로 유지한다.

## 5. 공용 창고 거래 예약

양쪽 본문에 `pending_transfer`(초기 null), `applied_transfer_ids`(초기 [])를 예약한다. 향후 pending은 transfer_id/direction/items/state를 갖는다. **M4는 거래를 시작하지 않으며 non-null pending 발견 시 로드와 재저장을 막는다.** 파일별 원자성을 창고 거래 보장으로 주장하지 않는다.

M11에서 별도 거래 저널을 먼저 내구 기록하고 양쪽 반영을 ID로 중복 제거하는 재적용 정책을 구현한다. 확정되지 않은 거래는 두 파일을 직접 수정하지 않는다. 저널의 양쪽 완료 확인 전 기록을 제거하지 않는다. M11 게이트에는 각 기록 단계 강제 종료·중복 반영·손상 복구를 포함한다.

## 6. 제외 상태와 저장 시점

- 전투 중 공격/피격/무적/애니메이션, 투사체, 적 HP/추적/리스폰 타이머, 바닥 드롭, 카메라, 일시적 버프·검투사 분노는 저장하지 않는다. 로드 후 적은 새 필드 초기 상태, 드롭은 소멸, 카메라는 플레이어를 따른다. UI에 필드 재구성과 미회수 드롭 제외를 안내한다.
- 보스 처치·영구 월드 변화는 이후 world.flags에 저장한다. 현재 보스 진행 구현을 주장하지 않는다.
- HP/MP가 살아 있고 사망 시퀀스·입력 잠금·공격·대시·스킬·임시 버프·쿨다운이 끝난 안전 상태만 저장한다. 사망 페널티 진행 중 파일을 만들지 않는다.
- 수동 슬롯 저장이 기본이다. 자동 저장은 활성 슬롯이 있는 상태에서 3분 주기로 요청하고 안전해질 때만 실행한다. 활성 슬롯이 없거나 손상/미지원 파일이면 임의 슬롯 생성·덮어쓰기를 하지 않는다. 종료 직전 강제 자동 저장은 하지 않는다.
- 자동 저장 UI와 슬롯 표시를 제공한다. 로드/새 캐릭터는 현재 미저장 진행을 버린다는 확인 후 수행한다.

## 7. Claude 리뷰 반영 상태

H1 거래 예약·미완 거래 차단, H2 G4 통일, H3 계층 검증, H4 버전 정책을 본문에 확정했다. M1 문자열 장비 슬롯·레지스트리, M2 제외 상태, M3 날짜/경과 시간 저장과 낮밤 파생, M4 필드 재구성, M5 자동 저장·사망 금지를 포함한다. 실제 구현 통과 여부는 실행 계획의 작업 기록과 테스트로 보고한다.

M3 제안 중 `is_day`의 별도 저장은 채택하지 않는다. `game_clock.gd::_refresh_phase()`가 경과 시간과 시간 설정으로 낮/밤을 계산하므로 중복 저장 시 서로 모순되는 상태가 생긴다. 날짜·경과 시간을 복원한 뒤 같은 함수로 위상을 재계산한다.

**현재 구현 경계**: 파일 계층만 구현했다. 게임 상태 스키마 검증, 미완 거래 차단, 계정/캐릭터 결합 검증과 메뉴 연결은 후속 작업 단위다. 예약 필드와 정책이 문서에 있다고 실제 런타임 기능이 완료된 것으로 판단하지 않는다.
