## 1. 판정과 점검 범위

**전투 중심 M3 빌드의 기존 테스트는 통과하지만, 장기 RPG 진행을 연결하기 전에 해결해야 할 결함과 설계 공백이 있다.** 특히 아이템 소유권 보존, 전직 후 강화 보존, 도감 완성 조건, 저장용 식별자가 우선이다.

| 범위 | 이번 확인 | 한계 |
|---|---|---|
| 공개 문서 46개 | 전반의 구성·미결 항목·이력·상호 참조를 훑고 핵심 계약을 상세 대조 | 모든 문장을 개별 검증했다는 뜻은 아님. 반전 원문은 공개 감사 대상에서 제외 |

## 2. 우선 수정할 문제

### A01 · P1 · 가방 포화 상태에서 장착 해제·교체 시 아이템 유실 — 재현됨

- **근거**: [inventory_component.gd](../../godot/scripts/items/inventory_component.gd)의 `equip()`·`unequip()`(134~161행).
- **재현 ①**: 기존 무기 A 장착→가방을 B로 채움→A 해제. 장착 상태를 먼저 지운 뒤 `add_to_bag()` 실패를 무시하므로 A가 가방과 장비 모두에서 사라진다.
- **재현 ②**: 가방 1칸에 B 2개를 중첩 보관→B 장착. B가 1개 남아 빈칸이 생기지 않으므로 반납할 A가 유실된다. 단순히 “장착하면 가방 한 칸이 빈다”는 전제가 성립하지 않는다.
- **수정 방향**: 반납 공간과 중첩 가능 여부를 먼저 검사하고 모든 변경을 함께 성공시키거나 함께 취소한다. 실패 시 기존 소유·장착 상태 보존.
- **완료 기준**: 가방 포화·같은 종류 중첩·반지 2슬롯·연속 교체에서 아이템 총수와 소유권 보존. 실제 인벤토리 UI는 아직 스텁이므로 **현재 컴포넌트 결함이며 일반 UI로 재현한 것은 아니다**.

### A02 · P1 · 2차 전직으로 교체되는 스킬의 투자 포인트가 묶임 — 실제 플레이어 씬 재현

- **근거**: [player_job_transition.gd](../../godot/scripts/progression/player_job_transition.gd) `perform_transition()`·[player_skill_points.gd](../../godot/scripts/progression/player_skill_points.gd), [검투사 스킬](../design/systems/m3-warrior-tier2-skills.md) 1-1절.
- **재현**: 전사 전직→분쇄 베기 Lv2 강화→Lv40 검투사 전직. 슬롯은 검투 선풍으로 교체되지만 새 스킬은 Lv1이고 기존 분쇄 베기 Lv2·소비 포인트가 그대로 남는다. 현재 리스펙도 미구현이다.
- **영향**: 새 스킬이 기본적으로 강해지는 것과 별개로, 사용 불가능해진 스킬에 쓴 포인트를 활용할 수 없다. [성장](../design/systems/growth.md) 6장의 “15개 스킬·풀업 118포인트” 예산도 **누적 습득과 슬롯 교체의 관계**를 정하지 않으면 실제 빌드 예산이 되지 못한다.
- **수정 방향**: 같은 스킬 계보로 강화 승계하거나 교체되는 스킬의 투자분만 환급하는 규칙을 확정한다. 강화·보너스 지급·슬롯 교체를 한 전직 처리로 묶는다.
- **완료 기준**: 강화한 슬롯4/Q/E를 전직한 뒤 투자 가치가 보존되고, 전직 반복 호출·저장 복원에서 포인트가 늘거나 사라지지 않음.

### A03 · P1 · 통합 도감 최종 보상에 자기 자신을 요구하는 순환이 남아 있음 — 설계 차단

- **근거**: [수집](../design/systems/collection.md) 3-2·4-1·4-4절. 칭호는 획득 시 도감 등록되고, 4종 도감 통합 100% 보상이 영웅 칭호 ‘만물의 기록자’다.
- **문제**: 이 칭호를 칭호 도감 분모에 포함하면, 받기 전에는 칭호 도감 100%가 불가능하다. 문서의 분모 제외 규칙은 비공개 칭호에 대해서만 적혀 있다. 펫 보상의 순환은 수정했지만 **통합 보상 칭호 순환은 미해소**다.
- **수정 방향**: 최종 보상 칭호를 완성 판정 분모에서 별도 제외하거나, 최종 보상 이전의 수집 대상만으로 완료를 판정한다. 칭호 총량·스탯 예산은 별개로 유지 가능하다.
- **완료 기준**: 보상 의존 그래프에 자기 참조가 없고, 정상 획득 순서로 최종 보상까지 도달함. 직업 변경·펫 30→60종 확장 때 이미 받은 구간 보상을 재지급하는지도 정의.

### A04 · P1 · 저장의 안정적인 ID 규칙과 현재 스킬 식별 방식이 충돌 — Phase A 선결

- **근거**: [진행 현황](../PROJECT_STATUS.md) 11-2절은 표시 이름을 저장 ID로 쓰지 않도록 규정한다. 반면 [player_skill_points.gd](../../godot/scripts/progression/player_skill_points.gd) 14~17행·[skill_tab.gd](../../godot/scripts/ui/skill_tab.gd)는 `skill_name`을 강화 상태의 키로 사용한다.
- **영향**: 스킬 이름을 고치면 저장된 강화 상태가 다른 스킬처럼 보인다. 같은 표시 이름을 쓰는 신규 직업도 충돌할 수 있다. A02의 계보 이전과도 연결된다.
- **수정 방향**: 변경되지 않는 `skill_id`와 표시명을 분리하고, 기존 이름 키에서 새 ID로 이전하는 표를 마련한다. 교체 전후 계보는 명시적인 ID 매핑으로 처리한다.
- **완료 기준**: 표시 이름 변경 후 강화 유지, 동명 스킬 구분, 알 수 없는 ID·버전 불일치 처리. 세이브 구현 뒤로 미룰 경우 저장 포맷 재작업이 발생한다.

## 3. 현재 구현의 추가 공백

### A05 · P2 · 일반 포션 입력이 인벤토리 수량·아이템 회복량을 우회

- **근거**: [player_controller.gd](../../godot/scripts/player/player_controller.gd) 674행은 `quickslot_1`에 `_stats.use_potion()`을 직접 호출한다. [player_stats_component.gd](../../godot/scripts/player/player_stats_component.gd)는 호출자가 보유 여부를 검사해야 한다고 명시한다. [inventory_component.gd](../../godot/scripts/items/inventory_component.gd)의 수량 차감 API는 이 경로에서 호출되지 않는다.
- **검증 범위**: 빈 가방에서 해당 **회복 API**가 HP를 회복하는 것은 진단 도구로 확인했다. 물리 키 입력을 재현한 것은 아니며, 단축키와 API의 연결은 소스로 확인했다.
- **영향**: 현재 일반 입력은 포션 보유·차감과 무관하게 기본 30% 회복을 호출한다. 기존 경제 문서의 포션 비용·하급 포션 100 회복과 일치하지 않으므로 소비 경제·포션 부족 난이도 판정에 사용할 수 없다.
- **완료 기준**: 일반 입력은 보유 아이템 ID→사용 가능 여부→고정 회복량→성공 시 1개 차감으로 연결. 수량 없는 디버그 회복을 유지한다면 별도 디버그 경로로 구분.

### A06 · P2 · 장착·소비 API의 제한 검사가 부족

- **근거**: [ItemData](../../godot/scripts/items/item_data.gd)에 `level_limit`가 있지만 현재 스크립트에서 이 필드는 드랍 후보 필터에만 사용된다. `InventoryComponent.equip()`에는 플레이어 레벨·직업 검사, `use_potion()`에는 아이템 종류·레벨 검사가 없다.
- **예시**: Lv30 제한 `POT-HP-2`를 낮은 레벨에서 획득했을 때 사용을 막는 계약이 없다. 재서임 후 이전 계열 무기 처리도 연결돼야 한다.
- **완료 기준**: UI 표시와 컴포넌트 검사가 일치하고, 미충족 요청은 상태·수량을 바꾸지 않음. 실제 UI가 없는 단계의 **API 통합 선결 사항**이다.

### A07 · P2 · 골드 레벨 차 보정이 실제 드랍에 연결되지 않음

- **근거**: [경제](../design/economy/economy-foundation.md) 6-4절·[레벨링 명세](../design/systems/m3-leveling-spec.md) 7-2절은 EXP와 골드가 같은 레벨 차 배율을 쓰도록 한다. [drop_system.gd](../../godot/scripts/items/drop_system.gd) `_drop_gold()`는 몬스터 레벨·등급만으로 계산한다. EXP 경로는 [player_progression.gd](../../godot/scripts/progression/player_progression.gd)에서 보정한다.
- **영향**: 현재 고레벨 캐릭터가 저레벨 적을 반복 사냥해도 골드 감소가 적용되지 않는다. 또한 `calc_gold()`의 반복 보스 인자는 런타임 호출에서 전달되지 않는다. 보스는 미래 통합 항목이다.
- **완료 기준**: 같은 적에 대해 플레이어 레벨별 EXP·골드 보정 대조, 보스 최초/반복 기록 영속화. 최소 골드와 반올림도 함께 정의.

### A08 · P2 · 음수 버리기 수량으로 보유 수량 증가 — API 재현됨

- **근거**: [inventory_component.gd](../../godot/scripts/items/inventory_component.gd) `drop_item()`은 `quantity <= 0`을 검사하지 않는다.
- **재현**: `drop_item(id, -2)` 호출 시 `entry.quantity -= quantity`로 가방 수량이 2개 증가한다. 실제 UI 조작으로 음수를 보낼 수 있다는 뜻은 아니다.
- **완료 기준**: 0·음수·보유량 초과 요청은 거절하고 수량·시그널을 바꾸지 않는다. 수량을 받는 공개 API 모두 같은 규칙 사용.

### A09 · P2 · 시간 스킵 계약 미완성 + 하루 경과 신호 누락

- **근거**: [명성·영지](../design/systems/reputation-territory.md) 4장은 아침/밤까지 휴식을 허용하고, 3·5장은 일수입·주문·월간 이벤트를 게임 시간에 연결한다. [game_clock.gd](../../godot/scripts/world/game_clock.gd)의 `advance_time()`은 최종 낮/밤 상태만 비교한다.
- **재현**: 낮에서 하루를 한 번에 진행하면 일수는 2일째가 되지만 `day_started`·`night_started`가 모두 발생하지 않는다. 현재 작은 프레임 단위 진행과 다른 경로이며, 휴식·로드·큰 시간 점프를 붙일 때 문제가 된다.
- **설계 공백**: 휴식으로 넘긴 시간에도 영지 수입·알 부화·주간 초기화·이벤트를 전부 처리하는가? 그렇다면 무료 모닥불 반복 휴식으로 실플레이 시간당 수입 상한을 우회할 수 있다. 처리하지 않는다면 게임 일수와 개별 시스템 진행 시간이 달라진다.
- **완료 기준**: 자연 경과·휴식·로드·디버그 점프를 구분한 처리표, 여러 일/월을 넘기는 일괄 정산, 만료 이벤트 처리, 중복 지급 방지. 모든 과거 밤을 실제 스폰으로 재생하는 방식도 피해야 한다.

## 4. 수치가 상세해 보여도 근거가 더 필요한 설계

### A10 · P2 · 칭호 +65 예산의 환산 근거가 불명확

- **근거**: [성장](../design/systems/growth.md) 7장·[수집](../design/systems/collection.md) 3-1절은 일반 칭호 1개를 1차 스탯 0.25로 환산하면서 HP+5·MP+3·치명+0.05%를 예시로 든다.
- **문제**: 파생 공식의 해당 채널만 역산하면 각각 체력 0.5·지력 0.6·민첩 1.0에 해당한다. 다른 동시 효과가 빠지므로 완전한 1차 스탯 동등가치는 아니지만, **세 예시를 전부 0.25로 세는 별도 가중치도 없다**. `60×0.25+30+20=65`라는 합만으로 전투 상한을 검증할 수 없다.
- **완료 기준**: 100개 칭호별 실제 효과·해금 시점과 평가 규칙을 표로 만들고, 공격·생존에 편중 수집한 경우까지 검산. 예산을 바꿀지 예시 수치를 줄일지는 밸런스 결정.

### A11 · P2 · 펫 종족값 합계 100이 실제 전투 기여 +10%를 증명하지는 않음

- **확인된 정상 부분**: [펫 전수표](../design/systems/pet-species.md) 60행 전부 합계 100·항목 8~32·4의 배수. 12패턴 각 5종, 버프20/공격24/디버프16, 일반36/희귀18/영웅6, 포획36/부화10/구매·보상10/히든4가 일치한다.
- **남은 문제**: 1-2·1-4절은 민첩을 치명·공격 속도·이동 속도 여러 축에 연결하고, 방어는 제산 공식, 버프는 가동률을 사용한다. “한 점=실효 0.1%”라는 정의만으로 이 채널들의 실제 효과가 그렇게 환산되지는 않는다. 여러 버프의 곱과 생존 증가도 단순 합과 다르다.
- **완료 기준**: 항목별 최종 대상 스탯·분배·상한·중첩·지속/쿨다운·대상 수를 지정한 뒤 직업별 DPS/피격 허용량 계산. 현재 표는 **예산 정의와 부분 검산**이며 전 케이스 상한 증명으로 쓰지 않는다.

### A12 · P2 · 펫 육성 시간에서 활동 시간과 전체 플레이 시간을 혼용

- **근거**: [수집](../design/systems/collection.md) 2-3·6절은 동반 4.4h·목장 8.7h를 전체 플레이 시간처럼 사용한다. [성장](../design/systems/growth.md) 5-3절의 300마리/h는 경험치 활동 중 속도이고 활동 비율은 50%다.
- **검산**: 같은 전제를 적용하면 동반 `1,305/150=8.7h`, 목장 `1,305/75=17.4h`의 **전체 플레이 시간**이 필요하다. 4.4/8.7h는 계속 사냥하는 조건에서만 맞는다. 펫의 최종 획득 시점 이후 성장 시간도 필요하다. 전 펫 만렙은 완성 조건이 아니므로 도감 진행 차단과 구분한다.
- **추가 공백**: “몬스터 레벨 무관 1 XP라 저레벨 반복 사냥 최적화가 제거된다”는 근거도 반대다. 더 빨리 잡을 수 있는 적이 있다면 여전히 유리하다. 목장이 도시 하사 때만 열린다는 문구도 시설표의 부락 2슬롯 규칙과 달라 해금 조건이 필요하다.
- **완료 기준**: 활동 시간/전체 시간 명시, 목장 해금 시점·분수 XP 누적 규칙·저레벨 사냥 허용 정책 확정.

### A13 · P2 · 반복 퀘스트 EXP 상한과 이벤트 유효기간이 실행 규칙으로 닫히지 않음

- **근거**: [퀘스트](../design/quests/quest-structure.md) 4절은 일일 15~25마리분·주간 40~60마리분과 “해당 레벨 필요치 10% 이하”를 함께 명시한다.
- **반례**: Lv1 필요량 55의 10%는 5.5지만 가장 작은 일일 보상도 `15×5=75 XP`다. 레벨별 상한 장부·잔여량 절삭·다중 레벨업 처리 또는 해금 레벨 없이는 보상표만으로 상한을 지키지 못한다.
- **별도 불일치**: 같은 절의 왕국 이벤트는 “다음 달 소멸”, [명성·영지](../design/systems/reputation-territory.md) 5-1절은 지속 게임 3일이다.
- **완료 기준**: 레벨별 누적 상한과 초기화·보상 수령 시점·저장 상태를 명시하고 이벤트 종료 시점을 단일 규칙으로 맞춘다.

### A14 · P2 · 목표 연결 이후의 장비 성장·가방 정리 범위가 빠지기 쉬움

- **근거**: [장비·성장 배선](../design/systems/m3-gear-growth-wiring.md) 3절은 M3에서 장착이 전투 스탯에 영향을 주지 않도록 **의도적으로 분리**했다. [인벤토리 UI](../../godot/scripts/ui/inventory_tab_stub.gd)는 현재 스텁이다. 진행 현황 11장의 M4 A/B 제안에는 이 완성 작업이 독립 완료 조건으로 명확하게 묶이지 않았다.
- **영향**: 저장과 의뢰를 연결해도 “주운 장비로 강해짐”은 자동으로 생기지 않는다. 제안서의 “가방을 비우고 다시 보고”도 실제 가방 정리 UI가 없으면 수행할 수 없다. 상점 추가만으로 장착 스탯 중복 문제도 해결되지 않는다.
- **완료 기준**: 실제 장비를 스탯의 단일 계산에 반영하고 기존 B급 가상 기준선을 제거, 시작 장비 지급, 가방 정리·비교·장착 UX를 별도 범위로 배정. **현재 M3 범위 위반으로 단정하지 않는다**.

### A15 · P2 · 250시간·명성 관문·이벤트 수집은 아직 완주 경로 검증이 아님

- **근거**: [명성·영지](../design/systems/reputation-territory.md) 2-2절은 장별 서브 개방 비율 가정으로 공급을 추산한다. 실제 개별 서브 퀘스트·선행 조건 목록은 미완성이므로 특정 관문 전에 그 보상을 모두 얻을 수 있는지 증명되지 않았다.
- **이벤트 의존**: 월 1회, 직전 2회 중복 제외만으로 유형별 수집 완료를 보장하지 않는다. 만렙 후 50시간은 자연 경과로 약 3.3개월이다. 잔여 이벤트 종류가 많거나 명성 15,000 지정권을 아직 얻지 못했다면 수집 10h·이벤트 4h 배분을 넘을 수 있다. 시간 스킵 정책(A09)에 따라 결과가 달라진다.
- **완료 기준**: 우선 Lv1~10에 대해 실제 콘텐츠 ID·선행 조건·고정 보상·관문 전 공급·사냥 동선을 표로 작성한다. 이후 월별 이벤트와 획득하지 못한 보상 보완 경로를 검증한다. 480개 총량과 시간 추산을 먼저 바꿀 근거는 아직 없다.

### A17 · P2 · 아트 검증 1건 실패와 검증기 실행 조건 — 선재 결함 재확인

- `validate_clipping.py`: `mob_slime_crack_death.png`의 행0/1/2, 열3에서 아래쪽 2px 단면을 보고한다. 1/40 실패이며 이전 인수인계에도 등재된 결함이다. 이번에 신규 발생한 것으로 세지 않는다.
- 지면 9종과 팔레트 66파일은 통과했다. **이 통과를 전체 아트 완성·모든 몬스터 외형 정식화로 해석할 수 없다.** 예를 들어 현재 숲거미 씬은 들개 텍스처를 참조한다. 임시 아트와 정식화 범위를 구분해야 한다.
- Windows 기본 출력 인코딩에서는 지면·클리핑 검증기가 특수문자 출력 중 `UnicodeEncodeError`로 중단됐다. `python -X utf8`로 재실행하면 지면 통과·클리핑 실패 결과까지 정상 출력된다.
- 완료 기준: 해당 프레임 수정 후 재검증·실제 프리뷰 확인, 표준 검증 명령에 UTF-8 실행 조건 반영. 이번 감사에서는 이미지 수정·음악 제작을 하지 않았다.

### A18 · P3 · 합계·기존 제안서의 잘못된 해석

- 퀘스트 12장 상세표는 **77건·3,600마리분**이다. “약 75건”은 근사값으로 이해 가능하지만 제작 태스크 수는 77을 기준으로 잡아야 한다.
- 퀘스트 시간표의 퀘스트성 합은 **198h(79.2%)**이며 설명의 195h(78%)와 다르다. 전체 표 합계 250h는 맞다.
- 월드 패밀리 30행의 실제 유형은 **야수6·균열4·마법5·악마3·인간형3·식물3·언데드2·벌레/갑각/비행/거인 각1**이다. 설명의 야수7·균열5는 합계 32가 된다.
- 이전 플레이 경험 제안의 “강타 안내가 모험가와 맞지 않을 수 있음”은 과도한 의심이었다. 모험가 공용 슬롯에 강타·질주·응급 처치가 실제로 들어 있다. 고정 `경험치 +5`와 미래 스킬명 변경 대응은 별도 점검 대상이다.
- 대화 중 시간 정지는 기존 확정 규칙이다. 새 승인 항목처럼 제안하면 안 된다. 제안서에 정정했다.

## 7. 처리 순서와 재검증

1. **진행 손실 방지**: A01·A02. 회복 입력(A05)은 M3 난이도 관찰 전에 현재 제약을 알리고 정상 경로와 분리한다.
2. **저장 기반 선결**: A04 + A09의 시간 계약. A03의 도감 보상 분모도 저장 구조에 반영한다.
3. **정식 첫 의뢰 연결**: A14의 가방 정리 가능 여부를 먼저 정한 뒤 NPC→수락→처치→보고→보상→재개를 검증한다.
4. **경제·장기 성장**: A06~A08·A10~A15를 실제 데이터와 경계 테스트로 닫는다.
5. **문서 동기화·아트 잔여**: A16~A18. 과거 기록은 날짜를 붙여 보존하고 현재 작업 지시와 분리한다.
