## 1. 스톤샤드(Stoneshard) 아트 스펙 조사

확인 가능한 사실만 정리하고, 개발사 확인분과 커뮤니티 추정분을 구분한다.

| 항목 | 값 | 신뢰도 / 출처 |
|---|---|---|
| 기본 캐릭터 스프라이트 크기 | **20x36 px** | **개발사 확인** — Steam 토론에서 개발사(Wayfinder) 답변 |
| 스케일링 방식 | **픽셀 퍼펙트, 정수 배율(x2/x4/x8)만 지원** | **개발사 확인** — "모든 픽셀이 디스플레이 픽셀과 정렬돼야 하므로 비정수 스케일은 스프라이트를 왜곡한다" |
| 이동 그리드 / 타일 크기 | **32x32 px로 널리 통용** | **커뮤니티 통용값(개발사 공식 미확인)** — 32px 타일 그리드는 웹 검색으로 확정 인용을 확보하지 못함. 아래 비교의 32px는 "추정"으로 취급한다 |
| 엔진 | GameMaker | 개발사/GameMaker 쇼케이스 확인 |
| 캐릭터 신체 비율 | 약 4~4.5등신(사실적 성인 비율, 머리 ~8px 추정) | 추정 — 20x36 프레임·공개 스프라이트 이미지로부터 역산. 스타듀식 2.5등신 치비가 아님 |
| 팔레트 규모 | **소규모 고정 팔레트를 쓰지 않음** — 하이컬러 손채색, 재질당 명암 단계가 많고 볼륨감(입체 음영)이 강함 | 추정 — 스톤샤드는 32색급 제약 팔레트 게임이 아니라, 색 수 제한 없는 고밀도 명암 스타일 |
| 톤 | 어둡고 그림 같은(painterly) 저채도 다크 판타지 | 관찰 — 우리 프로젝트(밝음6:어둠4)보다 확실히 어두움 |

**스톤샤드 "룩"의 실제 구성 요소 (참고 대상 분해)**
1. **높은 픽셀 밀도**: 32px 타일(추정) = 우리/스타듀 16px 대비 **타일 면적당 픽셀 4배**. 디테일·음영을 넣을 공간이 두 배(선형) 넓다.
2. **사실적 캐릭터 비율**: 4~4.5등신. 치비 특유의 큰 머리가 없어 무겁고 진지한 실루엣.
3. **강한 명암**: 3단 램프로는 못 내는 다단계 볼륨 셰이딩. 제약 팔레트가 아니라 고색수 손채색.
4. **정수 배율 픽셀퍼펙트**: 이 원칙 자체는 우리도 이미 동일(Nearest·정수 줌).

즉 우리가 "참고"할 수 있는 레버는 **(1) 타일 픽셀 밀도, (2) 캐릭터 프레임/비율, (3) 명암 단계·팔레트** 세 가지다. 정수 배율(4)은 이미 일치한다.

## 2. 현황 대비 비교표

우리 확정값(STYLE_GUIDE 1장)과 스톤샤드를 나란히 둔다. 화면 수치는 1920x1080·정수 줌 기준으로 계산했다.

| 지표 | 스톤샤드 (32px 타일 추정) | 스타듀밸리 (참고, G2-2 기준) | **본 프로젝트 (현재 확정)** | 방향 판정 |
|---|---|---|---|---|
| 타일 크기 | 32x32 px | 16x16 px | **16x16 px** | 스톤샤드가 밀도 2배 |
| 타일 면적당 픽셀 | 1024 px | 256 px | **256 px** | 스톤샤드 4배 |
| 캐릭터 프레임 | 20x36 px | 16x32 px | **16x32 px** | 스톤샤드가 폭 +4·높이 +4 큼 |
| 캐릭터 신체 비율 | ~4.5등신(사실적) | ~2.5등신(치비) | **~2.5등신(치비)** | 방향 정반대 |
| **타일 그리드 대비 캐릭터** | 약 **0.6폭 × 1.1높이 타일** | 1폭 × 2높이 타일 | **1폭 × 2높이 타일** | ★ 아래 주 참고 |
| 화면 가로 타일 수 | 약 30타일(x2, 내부 960px 기준) | 약 30타일 | **30타일**(x4, 내부 480px) | 유사 |
| 화면 세로 타일 수 | 약 17타일 | 약 17타일 | **16.9타일** | 유사 |
| 캐릭터 화면 높이 점유율 | 36/540 = **6.7%** | 32/540 = 5.9% | **32/270 = 11.9%** | ★ 우리가 더 큼 |
| 팔레트 | 고정 소팔레트 없음(하이컬러) | 다색(제약 약함) | **EDG32(32색 고정)** | 우리가 가장 제약적 |
| 재질당 명암 단계 | 다단계 볼륨 셰이딩 | 3~4단 | **3단 램프 고정** | 스톤샤드가 훨씬 깊음 |
| 스케일링 | 정수 배율 픽셀퍼펙트 | 정수 배율 | **정수 배율(Nearest, zoom=4)** | 이미 일치 |

★ **반드시 짚어야 할 상충점 (핵심)**: 디렉터 배경 메모의 "스톤샤드 캐릭터가 더 큼"은 **절대 픽셀·사실적 비율** 기준으로는 맞지만(20>16, 36>32), **타일 그리드 대비로는 오히려 스톤샤드 캐릭터가 더 작다**(0.6폭×1.1높이 vs 우리 1폭×2높이). 화면 점유율로도 우리 캐릭터(11.9%)가 스톤샤드(6.7%)보다 크게 보인다 — 스톤샤드가 더 줌아웃돼 있어 캐릭터가 세계 속에서 작게 놓이기 때문이다. 따라서 "스톤샤드처럼"이 **두 가지 상반된 뜻**으로 갈린다:
- (A) **디테일·비율의 사실성** — 프레임 확대 + 사실적 등신 + 명암 심화. → **달성 가능·권장**.
- (B) **캐릭터를 세계 대비 더 작게(줌아웃)** — 이건 "캐릭터가 더 큼" 메모와 정면 충돌하며 실시간 액션 교전 가독성(회피 시야는 좋아지나 캐릭터 인지 저하)에도 영향. → **권장하지 않음**.

이 제안서의 모든 안은 (A) 해석을 채택한다. 만약 디렉터 의도가 (B)라면 별도 지시가 필요하다(9장).

## 3. 제안 (옵션 3안)

### 안 1 — 캐릭터/몬스터만 스톤샤드화, 타일 16px 유지 (추천)

**요지**: 가장 비싼 자산 카테고리인 타일셋·맵을 지키고, 플레이어가 오래 응시하는 캐릭터/몬스터에만 스톤샤드의 밀도·비율·명암을 적용한다.

| 변경 | 내용 |
|---|---|
| 타일 | **16px 유지** (변경 없음) |
| 줌/내부 해상도 | **zoom=4 / 480x270 유지** (변경 없음) |
| 플레이어 프레임 | 16x32 → **20x36**(스톤샤드 수치 직접 채택) 또는 24x40. 신체 비율 2.5등신 → **약 3.3등신**(스톤샤드 4.5와 스타듀 2.5의 중간 — 우리 톤 반영, 4장) |
| 몬스터 프레임 | 체급별 소폭 비례 상향(예: 경량 16x16→20x20, 표준 32x24→36x28, 중량 32x32→40x40). 실루엣 구분 원칙(STYLE_GUIDE 6-3) 유지 |
| 명암 | **캐릭터·몬스터에 한해 4단 램프 허용**(스톤샤드식 볼륨감). 타일·오브젝트는 3단 유지 |
| 팔레트 | EDG32 유지(확장하지 않음). 4단 램프는 32색 내 인접 명도 조합으로 구현 |

**파급효과**
- **재제작 규모**: 캐릭터(전사 1직업)·몬스터 3종은 **G2-2로 이미 재제작 예정**(STYLE_GUIDE 8장 — 구 32x32 자산 전부 재제작 필요). 목표 규격만 20x36/확대 체급으로 바꾸므로 **증분 비용 거의 0**. 타일셋·아이콘·오브젝트·UI 재제작 없음.
- **코드**: 콜리전 박스·발밑 앵커·y-정렬 오프셋 재튜닝(gameplay-dev, 소규모). combat.md 타일=px 환산·`project.godot` 줌/해상도 **불변**.
- **성능**: 무시 가능(캐릭터 몇 종의 프레임이 수 px 커질 뿐).
- **UI 좌표**: 영향 없음(UI는 CanvasLayer, 캐릭터는 월드).
- **G2-2와의 관계**: **부분 충돌**. "1타일 폭(16px) 슬림화"를 20px(1.25타일 폭)로 되돌린다. 단 G2-2의 진짜 목적("화면이 좁고 캐릭터가 뚱뚱해 보였다"의 해소)은 유지 — 20px는 구 32px보다 여전히 슬림하고, 뚱뚱함의 원인이던 2타일 폭에서 벗어나 있다. STYLE_GUIDE 1-2-1절 근거표는 "프레임 폭만 조정하면 됨"을 이미 인정하므로, 20px로의 조정은 그 논리의 연장선이다.

**리스크**: 16px 청키 타일 위에 고밀도(4단·36px) 캐릭터를 얹으면 **질감 불일치**(배경은 거칠고 캐릭터만 매끈) 가능성. 스톤샤드의 통일감은 타일·캐릭터가 모두 32px이기 때문이다. → M2 수직 슬라이스 실제 화면에서 반드시 눈으로 확인, 과하면 캐릭터 명암을 3.5단 수준으로 절제.

### 안 2 — 전면 32px 밀도 정합 (순수 스톤샤드)

**요지**: 타일까지 32px로 올려 전 요소를 스톤샤드급 밀도로 통일한다. "진짜 스톤샤드 비율".

| 변경 | 내용 |
|---|---|
| 타일 | 16px → **32px** (전 타일셋 재제작) |
| 캐릭터 | 24x48 등 32px 밀도로 재정의, 사실적 비율 |
| 줌 | zoom=4 → **x2**(내부 960x540, 가로 30타일 유지) 또는 x3(가로 20타일, 더 줌인) — 정수 유지 필수. **디렉터 결정 필요** |
| combat 수학 | 대시 3타일=48px → **96px** 등 `combat.md`의 타일=px 환산 전부 2배 재작성 |
| 팔레트/명암 | EDG32 유지 가능하나, 스톤샤드 명암 심도를 내려면 램프 4단+ 상시화(또는 팔레트 확장 검토) |

**파급효과**
- **재제작 규모**: **최대**. 동부 변경 타일셋 등 **타일셋 전면 재제작** + 캐릭터/몬스터/오브젝트/아이템 아이콘 밀도 재정의. CC0 16px 생태계(Kenney 등)가 대부분 16/32px인데, 소싱 대상이 32px로 바뀌면 재소싱·재드로잉 필요.
- **코드**: `project.godot` 줌·픽셀 스냅 재설정, `combat.md` 및 이를 참조하는 전투 코드의 타일=px 환산 전면 수정, 콜리전/그리드 재정의.
- **UI 좌표**: 대체로 무관(CanvasLayer)이나, 월드 좌표에 의존하는 HUD 요소(데미지 팝업 위치 등) 점검 필요.
- **성능**: 텍스처 메모리 타일당 4배(2D라 경미하나 0은 아님).
- **G2-2와의 관계**: **전면 충돌**. G2-2는 "타일 16px·줌 x4는 스타듀와 동일하니 유지"를 명시 확정했다. 안 2는 이 결정을 폐기한다.
- **1인 개발 적합성**: 낮음. 250시간 분량 맵의 타일셋을 32px로 다시 그리는 것은 수 주 단위 추가 부담.

### 안 3 — 절충 24px 타일

**요지**: 16과 32의 중간(24px 타일 + 24x40 캐릭터).

**파급효과**
- 밀도는 스톤샤드에 근접하나, **24px는 CC0 픽셀아트 생태계에서 비표준**(16/32가 사실상 표준)이라 소싱 이점이 거의 없어 대부분 재제작해야 한다.
- 24px 타일 x4 = 96px → 1920 화면에 가로 20타일(줌인됨). x2는 48px → 40타일(줌아웃 과다). 정수 줌 선택지가 어중간.
- 결과적으로 **안 2의 재제작 부담 대부분을 지면서 표준 자산 이점은 없음**. **비권장.**
